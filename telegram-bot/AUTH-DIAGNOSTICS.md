# Диагностика SETUP_KEY с iPhone

Публичная служебная страница: https://nikolay-transport-start.anufrii2020.workers.dev/setup .
Она относится только к обработчику бота. Визитка, её четыре ссылки, Mini App и Menu Button не меняются.

## Что изменено в setup-auth-v2

- `sameSecret` по-прежнему сравнивает два значения точно через SHA-256 и полный XOR результатов. Значения и хеши не выводятся. Дополнительно проверяется тип аргумента.
- Устранено ограничение SETUP_KEY только буквами, цифрами, `_` и `-`: теперь допускается 20–256 печатных ASCII-символов, включая знаки пароля. Пробелы, переводы строк и не-ASCII в сохранённом секрете не допускаются. Для генератора на странице формат остаётся прежним: случайный base64url.
- Схема `Bearer` распознаётся без учёта регистра, с допустимыми HTTP-пробелами между схемой и ключом. Сам ключ сравнивается точно. В Safari отключены автозамена/капитализация; случайные пробелы по краям вставленного значения удаляются только в поле страницы.
- При отказе сохраняется HTTP 403 и `error: forbidden`, но добавляется безопасный `reason`. Это не отключает авторизацию.
- Кнопка «Проверить ключ без Telegram» выполняет авторизованный `POST /setup` с действием `diagnose`. Она не вызывает Telegram API и ничего не меняет.
- Страница и диагностические ответы показывают только фиксированную ревизию кода, UUID версии Cloudflare и булевы признаки. Значения, части, длины и хеши секретов не отображаются. UUID версии — идентификатор развёртывания, не хеш ключа.

## Действия в Safari

1. Дождитесь успешной сборки **Workers Builds: nikolay-transport-start** для коммита обновления в GitHub. В Cloudflare откройте **Workers & Pages → nikolay-transport-start → Deployments**. Убедитесь, что новая версия активна в Production и получает 100% трафика.
2. Откройте публичный адрес `/setup` выше в новой вкладке Safari и обновите страницу. Не используйте Preview редактора или адрес отдельной старой версии.
3. Раскройте **«Активная версия и наличие секретов (без значений)»**. Должны отображаться `revision: setup-auth-v2`, UUID версии и `setup_key_present: true`. `setup_key_format_valid` также должен быть `true`.
4. Сверьте `worker_version_id` с активной версией на странице Cloudflare **Deployments**. После изменения Secret UUID может отличаться от первоначального GitHub Build — это нормально: изменение секретов создаёт новую версию. Важно совпадение с действующим Production-развёртыванием.
5. Вставьте **сохранённое значение SETUP_KEY** из менеджера паролей. Не вставляйте `SETUP_KEY=`, текст `Bearer ` или дополнительные кавычки. Не нажимайте генерацию новых секретов для обычной проверки.
6. Нажмите **«Проверить ключ без Telegram»**. Успех: `ok: true`, `diagnostics.authenticated: true`, `telegram_checked: false`. Это подтверждает ключ, но ещё не работу бота.
7. Затем нажмите **«Проверить подключение»**. Только эта проверка обращается к Telegram; она не перенастраивает webhook. Если webhook уже подключён сюда, повторно подключать его не нужно.
8. Если он ещё не подключён и другой обработчик бота не используется, нажмите **«Подключить webhook»**. После этого вручную отправьте `/start` в личный чат @NikolayTransportBot и проверьте ответ и кнопку.

Не присылайте SETUP_KEY, BOT_TOKEN или WEBHOOK_SECRET. Для диагностики можно скопировать **только текст результата** и блок активной версии: в них нет секретов. Не делайте снимок раскрытого генератора со значениями.

## Как понимать отказ

| reason / признак | Что установлено | Что сделать |
| --- | --- | --- |
| `setup_key_missing` | Активный Worker не видит непустой строковый SETUP_KEY | Открыть **Settings → Variables and Secrets** именно Worker `nikolay-transport-start`, а не Build variables. Добавить/применить SETUP_KEY как Secret и нажать **Deploy**. |
| `setup_key_invalid_format` | Привязка есть, но не соответствует формату | При необходимости Rotate **только SETUP_KEY**. Использовать сохранённый случайный ключ 20–256 печатных ASCII-символов без пробелов/переводов строк. Нажать Deploy. |
| `authorization_missing` | Заголовок не дошёл до обработчика | Заново открыть публичный `/setup` в Safari. Штатная страница отправляет заголовок сама; не используйте Preview, перенаправляющий адрес или промежуточный прокси. |
| `authorization_invalid_format` | Заголовок получен, но его формат неверен | Вставить только значение ключа и повторить проверку. |
| `key_mismatch` при `authorization_format_valid: true` | Заголовок дошёл, формат верен, но введённое значение не совпадает с привязкой активной версии | Сверить сохранённый ключ и активную Production-версию. Если значение утеряно, Rotate только SETUP_KEY и Deploy; BOT_TOKEN и WEBHOOK_SECRET не менять. |
| `bot_secrets_format_valid: false` | BOT_TOKEN или WEBHOOK_SECRET отсутствует/имеет неверный формат в активной версии | Проверить наличие привязок и применение уже сохранённых секретов в Production. Не пересоздавать их вслепую. Проверка ключа `diagnose` всё равно может пройти. |

Если на странице нет `setup-auth-v2`, сначала исправьте выбор/публикацию версии. Не нужно повторно менять ключ, пока открыт старый Worker.

## GitHub Builds и Production Secrets

- В репозитории задан Worker `nikolay-transport-start`, корневая папка `telegram-bot`. Production-команда — `npx wrangler deploy`, без `--env`, `--secrets-file` и команд записи/удаления секретов. В конфигурации нет значений BOT_TOKEN, WEBHOOK_SECRET или SETUP_KEY и нет одноимённых `vars`.
- Обычный `wrangler deploy` публикует новую версию кода и сохраняет Secrets. Флаг `keep_vars` управляет обычными текстовыми Variables и не является исправлением потери Secret.
- **Build variables/secrets** доступны процессу сборки, а не автоматически `env` работающего Worker. Нужны **Settings → Variables and Secrets** Worker. Именованные Wrangler-окружения имеют отдельные секреты; в этом проекте именованных окружений нет.
- После Rotate/добавления Secret нажмите **Deploy**, если панель это предлагает. Сохранённая, но не развёрнутая версия или старая версия с частью трафика может продолжать получать запросы с прежним SETUP_KEY.
- Для фактической проверки сохранения ключа при следующей сборке: сначала получите `authenticated: true` через `diagnose`, затем после сборки повторите проверку **тем же сохранённым ключом**. Новый UUID с `authenticated: true` подтверждает работоспособность ключа после конкретного развёртывания. Одно лишь `setup_key_present: true` не доказывает совпадение значения между версиями.
- Без доступа к панели Cloudflare нельзя проверить всю историю Rotate/Deployment или доказать, какое значение было сохранено ранее. Диагностика показывает состояние версии, которая действительно обработала запрос, а не состояние черновика в панели.

## Границы проверки

Тесты с синтетическими ключами проверяют сравнение, передачу Authorization, причины отказов, отсутствие утечек и запрет неавторизованных вызовов Telegram. Они не доказывают, что реальный SETUP_KEY владельца принят на Production. Для этого нужен шаг 6 на iPhone; для подтверждения работы приветствия — реальный `/start` после подключения webhook.
